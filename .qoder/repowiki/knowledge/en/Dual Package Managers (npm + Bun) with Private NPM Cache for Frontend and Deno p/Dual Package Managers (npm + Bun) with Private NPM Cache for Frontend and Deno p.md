## What system/approach is used

The RepairPro monorepo manages dependencies in two separate layers:

1. **Frontend (Vite/React SPA)** — declared via `package.json` with both `dependencies` and `devDependencies`, and locked by a `package-lock.json` (lockfileVersion 3). A `bun.lock` file also exists, indicating the project has been resolved with Bun as an alternative package manager.
2. **Supabase Edge Functions** — each function lives under `supabase/functions/<name>/index.ts`. There is no shared backend dependency manifest; instead, individual functions that need third-party packages declare them through per-function `deno.json` files (e.g. `supabase/functions/auth-email-hook/deno.json` pins React JSX compiler options and types), while others use an empty `{}` deno config and rely on Deno's built-in or bundled runtime modules.

There is no vendoring of source code into the repo — all third-party packages are fetched from registries at install/build time.

## Key files and packages

- `package.json` — single-source-of-truth for frontend runtime and dev dependencies (React 18, Vite 5, Radix UI primitives, TanStack Query, Supabase JS client, i18next, framer-motion, three.js, etc.).
- `package-lock.json` — deterministic lockfile for npm installs; contains exact resolved URLs and integrity hashes for every transitive dependency.
- `bun.lock` — parallel lockfile generated by Bun; its `packages` section shows many entries resolved from `https://europe-west1-npm.pkg.dev/lovable-core-prod/sandbox-npm-cache/...`, revealing a private Google Artifact Registry mirror.
- `supabase/functions/*/deno.json` — per-function Deno configuration. The `auth-email-hook` function explicitly pins `react@18.3.1` and `@types/react@18.3.1` via `compilerOptions.jsxImportSource` and `types`, showing how Deno-side deps are versioned per-function rather than globally.
- `supabase/config.toml` — Supabase project configuration (migrations, functions, etc.) but does not list function-level dependencies; those live alongside each function.

## Architecture and conventions

- **Single-package frontend**: All frontend dependencies are co-located in one `package.json`; there are no npm workspaces or sub-packages. Dev-only tooling (eslint, vitest, typescript, tailwind, postcss, vite-plugin-pwa, testing-library) is separated into `devDependencies`.
- **Lockfiles committed**: Both `package-lock.json` and `bun.lock` are checked into the repository, ensuring reproducible installs across environments. The presence of both suggests developers may switch between npm and Bun locally, but only one should be authoritative at a time to avoid drift.
- **Private registry usage**: The `bun.lock` resolves many packages from `europe-west1-npm.pkg.dev/lovable-core-prod/sandbox-npm-cache`, meaning builds run inside Lovable's sandbox environment pull from a private Google Cloud Artifact Registry cache rather than directly from `registry.npmjs.org`. Some entries still resolve from `registry.npmjs.org` (visible in `package-lock.json`), so the effective registry depends on which lockfile is used and what `.npmrc` / Bun config is active at install time.
- **Per-function Deno configs**: Each Supabase Edge Function is self-contained. Only functions that import non-standard libraries (like React JSX templates in `auth-email-hook`) carry a `deno.json`; others ship without one. This keeps the backend surface minimal and avoids pulling unnecessary packages into the edge runtime.
- **No shared backend dependency graph**: Unlike the frontend, there is no central `deno.json` or `package.json` aggregating all Edge Function dependencies. Sharing happens through the `_shared/` directory containing TypeScript/JS code reused across functions (email templates, notification templates).

## Conventions and constraints

- Dependencies are pinned with caret ranges (`^x.y.z`) in `package.json`, allowing minor/patch updates automatically; exact versions are enforced by the committed lockfiles.
- Frontend dependencies are split strictly between `dependencies` (runtime: React, Supabase client, UI libs, i18n, PDF/Excel tools) and `devDependencies` (build/tooling/test); nothing appears in both.
- Supabase Edge Functions do not maintain a global dependency manifest; any external package must be referenced by the function's own `deno.json` or imported from `_shared/`. This is enforced by the Deno runtime when deploying to Supabase.
- No `.npmrc`, `.yarnrc`, `pnpm-workspace.yaml`, `go.mod`, or `vendor/` directories were found — the project relies exclusively on npm/Bun registries (public and cached) and Deno's module resolution.
- Database schema changes are managed separately via SQL migration files under `supabase/migrations/` and are not part of the dependency management concern.
