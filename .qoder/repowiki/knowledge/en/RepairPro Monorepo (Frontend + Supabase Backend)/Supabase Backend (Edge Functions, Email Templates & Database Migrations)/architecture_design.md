The module is organized into three layers under `supabase/`:

- **Edge Functions** (`functions/`): Each directory is an independent Deno `Deno.serve` handler registered in `config.toml`. Most functions declare `verify_jwt = false`, meaning they are invoked by Supabase internal triggers or service-role callers; only `process-email-queue` enforces JWT role checks (`service_role`) as defense-in-depth. The entry points split into two families: (1) auth-triggered handlers (`auth-email-hook`, `signup-guard`, `request-reset-code`, `send-password-reset`, `update-password-with-token`, `verify-reset-code`) that render React Email templates via `@react-email/components` and enqueue messages via the `enqueue_email` RPC; (2) operational/admin handlers (`admin-db-maintenance`, `admin-manage-users`, `create-employee`, `grant-trial`, `restore-live-db`, `wipe-employee`, `system-health-monitor`, etc.) that perform DB mutations directly.
- **Shared template layer** (`functions/_shared/`): `email-templates/*.tsx` are React components used by `auth-email-hook`; `_shared/notification-templates.ts` provides a mail-client-safe HTML shell with a `renderEmail(template_row, vars)` dispatcher keyed by `template_key`, plus an `esc` sanitizer and `SAMPLE_VARS` for preview/test flows. This layer is pure — no network calls — so it can be reused by both the webhook and the admin `send-notification-email` function.
- **Queue pipeline**: `auth-email-hook` writes to the `auth_emails` queue; `send-notification-email` writes to `transactional_emails`. Both use the same `enqueue_email` RPC. `process-email-queue` is the sole consumer: it reads batches via `read_email_batch` (with a 30s visibility timeout), sends auth emails through Lovable's built-in path (`sendLovableEmail`) and app emails through the Resend connector gateway (`connector-gateway.lovable.dev/resend/emails`), tracks outcomes in `email_send_log`, applies rate-limit backoff via `email_send_state.retry_after_until`, drops expired messages by TTL, and moves unrecoverable messages to DLQ queues via `move_to_dlq`.
- **Schema evolution** (`migrations/`): A flat, timestamp-prefixed SQL migration set (e.g. `YYYYMMDDHHMMSS_<uuid>.sql`) managed by Supabase CLI, covering tables, RLS policies, indexes, and stored procedures referenced by the functions (`enqueue_email`, `read_email_batch`, `delete_email`, `move_to_dlq`, `has_role`).

Dependency direction is one-way: functions depend on `_shared/*` and on the database via `@supabase/supabase-js` service-role clients; migrations have no code dependencies. There is no shared library between functions — each handler is self-contained and communicates with the rest of the system exclusively through Supabase RPCs and HTTP calls.
